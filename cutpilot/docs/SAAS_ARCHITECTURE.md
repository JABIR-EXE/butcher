# CutPilot account architecture — v1.8 hosted pilot

## Current status

Version 1.8 adds working owner registration, sign-in/out, email verification, password reset, public marketing/pricing pages and a separate SQLite workspace database per butcher business.

This is an **early hosted pilot foundation**, not a fully production-hardened SaaS. It has not been deployed to a public domain. It does not yet include subscription checkout, team invitations, multi-location operations, managed PostgreSQL, automated backups, external monitoring or a professional security review.

The normal local preview (`CUTPILOT_MODE=local`) remains a single-shop demo and has no customer accounts. Account testing uses `CUTPILOT_MODE=saas`.

## Request and data flow

1. A shop owner registers with their name, email, password, shop name, country, currency and a selected plan preference.
2. In hosted configuration, the app sends an email-verification link through the configured SMTP account.
3. The owner verifies the email, then signs in.
4. The server issues an opaque random session token in an HttpOnly, SameSite=Lax cookie. Only a hash of that token is stored in the central authentication database.
5. The session maps the signed-in owner to a membership and organization.
6. The organization ID is generated by the server. Its UUID determines its tenant SQLite file under `CUTPILOT_DATA_DIR/tenants/`.
7. For each authenticated API request, the server resolves that database from the session and selects it for the request thread. The browser cannot submit a database path or choose an organization ID.
8. Sign-out deletes the server-side session and expires the cookie. Password reset invalidates existing sessions.

## Databases

The central authentication database (`auth.sqlite3`) holds users, organizations, memberships, sessions, email tokens and billing-event placeholders.

Each organization gets a separate SQLite database file containing its shop products, suppliers, stock, sales, forecasts, waste and purchase records.

This file-per-organization structure is a simple isolation boundary for a small, single-instance pilot. It is **not the final scalable architecture**. It has operational costs: one host instance must own the persistent disk, backup/restore must capture the central database and every tenant file, and horizontal scaling is not supported.

## Hosted deployment model in this release

The included `render.yaml` is a deployment template for one paid Render Python web service with a persistent disk mounted at `/var/data/cutpilot`.

Required settings include:

```env
CUTPILOT_MODE=saas
CUTPILOT_HOST=0.0.0.0
CUTPILOT_DATA_DIR=/var/data/cutpilot
CUTPILOT_BASE_URL=https://your-real-domain.example
CUTPILOT_REQUIRE_EMAIL_VERIFICATION=1
CUTPILOT_COOKIE_SECURE=1
CUTPILOT_SMTP_HOST=your-transactional-email-host
CUTPILOT_SMTP_PORT=587
CUTPILOT_SMTP_USER=your-smtp-user
CUTPILOT_SMTP_PASSWORD=your-smtp-password
CUTPILOT_EMAIL_FROM=CutPilot <noreply@your-domain.example>
```

Use the actual domain and credentials supplied by the adult/business owner. Store secrets in the hosting provider's environment settings, never in source control. Verify SMTP delivery, HTTPS, account recovery and session behavior before opening registration.

The Render Blueprint is a starting template only. It does not create a domain, email provider, billing account, company or customer support operation on your behalf.

## What must happen before accepting customer data

- Have an experienced developer review the standard-library HTTP server and authentication/session handling. Use a maintained production web framework and server before public launch.
- Use managed PostgreSQL for the durable multi-tenant service. Store `organization_id` on every business-owned record, enforce server-side membership checks and database-level row-level security.
- Add automated tests for cross-tenant read/write access on every API endpoint, imported files and exports.
- Add private object storage for imports with strict file-size/type validation, retention and deletion policies.
- Add rate limiting at the hosting edge, security headers, CSRF protections where appropriate, audit logging and error monitoring.
- Schedule encrypted backups and perform restore drills for both account and business data.
- Implement account deletion, data export, team invitation/roles and support workflows.
- Have privacy notice, terms, refund/cancellation, tax and customer-support processes reviewed for the markets served.
- Keep public registration invite-only until the above checks are complete.

## Future PostgreSQL target

A scalable next version should use a managed PostgreSQL database. Recommended core tables:

- `users` / authentication provider user IDs
- `organizations`
- `organization_members`
- `locations`
- `products`
- `stock_batches` and `stock_movements`
- `sales` and `sale_items`
- `suppliers` and `supplier_products`
- `purchase_orders` and `purchase_order_items`
- `forecasts` and `forecast_runs`
- `waste_events`
- `subscriptions` and `billing_events`
- `audit_events`

Every business-owned row must carry an organization/location relationship. Enforce row-level policies in the database as well as authorization in the application. Keep billing webhooks and service credentials server-side.

## Payment integration status

The site includes public plans and proposed pricing. The registration form stores the selected plan as a preference, and new organizations start with `subscription_status='pilot'`. **No payment is collected and no paid subscription is activated.** See `GETTING_PAID_AND_SIGNUPS.md` for the proposed provider evaluation and the steps required to implement checkout safely.
